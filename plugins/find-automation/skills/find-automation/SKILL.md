# find-automation

사람들은 "AI로 뭘 자동화하고 싶어요?"라는 질문에 잘 답하지 못한다. 반복 작업이 너무 익숙해서 반복처럼 느껴지지 않기 때문이다. 이 스킬은 실제 세션 기록에서 그 반복을 찾아 근거와 함께 보여 주고, 사용자가 고르면 실제로 자동화까지 만든다.

## 지켜야 할 원칙 (이유와 함께)

- **분석은 로컬에서만.** 세션 기록에는 사내 코드, 고객 데이터, 자격증명이 섞여 있다. 세션 내용을 WebSearch·WebFetch·MCP 도구·외부 API로 보내지 않는다. 분석 결과나 세션 원문을 파일로 복사·저장하지 않는다(임시 파일 포함). 스크립트 출력은 stdout으로 읽고 끝낸다.
- **민감정보는 마스킹된 상태로만 보여 준다.** `scan_sessions.py`가 토큰·키·비밀번호·이메일을 가리지만 완벽하지 않다. 사용자에게 보여 줄 인용문에 비밀처럼 보이는 값이 남아 있으면 직접 `<MASKED>`로 바꾼다. 원문 전체를 보여 주지 말고 필요한 부분만 짧게 인용한다.
- **파일 생성·수정 전에는 항상 확인받는다.** 무엇을 어디에 만들고 고치는지 보여 준 뒤 승인을 받는다. 특히 `settings.json`처럼 전역에 영향이 가는 파일은 바뀌는 부분을 diff로 보여 준다.
- **환경 의존성을 최소화한다.** 자동화를 만들 때 python3 표준 라이브러리, POSIX 셸, 이미 설치된 CLI만 사용한다. 새 의존성이 꼭 필요하면 이유를 말하고 확인받는다.

## 인자

`/find-automation [기간] [프로젝트...] [off|on|config ...]`

- 기간: `30d`(기본), `90d`, `2w`, 또는 `since 2026-09-01`. 원본 세션 파일은 보통 30일 남짓만 남는다. 그보다 이전 구간은 스크립트가 `history.jsonl`의 프롬프트로 자동 보충하며, 이때는 명령어나 작업 흐름 근거가 없다는 점을 사용자에게 알린다.
- 프로젝트: cwd에 포함된 문자열(예: `my-api`). 여러 개를 줄 수 있다. 없으면 전체 프로젝트.
- `off`/`on`: 세션 시작 제안 끄기/켜기 → `state.py config session_prompt off|on`
- `hint off|on`: 키워드 힌트 끄기/켜기 → `state.py config keyword_hint off|on`
- `config interval 7`: 제안 주기 변경 → `state.py config interval_days 7`

설정 인자만 받았다면 해당 명령을 실행하고 결과를 한 줄로 알려 준 뒤 끝낸다.

## 진행 순서

아래 스크립트 경로는 이 스킬의 base directory 기준이다(`<skill>/scripts/...`).

### 1단계: 세션 분석

1. 먼저 `python3 <skill>/scripts/state.py mark-run`을 실행한다. 이렇게 해야 세션 시작 훅이 다음 주기까지 다시 제안하지 않는다.
2. `python3 <skill>/scripts/scan_sessions.py summary --days N [--project X ...]`를 실행한다. 출력에는 다음 섹션이 있다.
   - **P# 반복 요청**: 비슷한 프롬프트 묶음 (횟수, 세션 수, 회당 추정 소요 분, 근거 세션)
   - **T# 비슷한 주제의 세션**: ai-title 묶음. 같은 종류의 일을 여러 세션에서 했다는 신호
   - **1-c 짧은 승인 응답**: "계속 진행해줘" 같은 응답 반복. Claude가 불필요하게 멈춘다는 신호
   - **C#/CC# 자주 실행하는 명령어**와 거의 그대로 반복된 복합 명령
   - **F# 반복되는 작업 흐름**: 도구·명령 순서 (예: `git add → gh pr create → gh pr checks → gh pr merge`)
   - **R# 반복되는 정정·지적**
   - **5. 이미 쓰고 있는 스킬/커맨드**: 이미 자동화된 것을 후보에서 빼기 위한 정보
3. `python3 <skill>/scripts/scan_sessions.py cards --days N [--project X ...]`도 함께 실행한다. 세션마다 한 줄씩, 제목·첫 요청·태그(첨부문서, 이미지, 타인발 요청?, 공지·가이드, Confluence작성, 웹조사, AWS, PR 등)를 보여 준다.
   **summary만으로는 부족하다.** summary는 글자 유사도와 명령어 빈도로 반복을 찾기 때문에 개발 작업만 잘 잡는다. 리서치, 문의 대응, 문서화, 권한 관리처럼 매번 표현이 다른 업무는 cards를 읽고 의미 단위로 직접 묶어야 보인다. 실제로 사용자의 반복 업무 대부분이 이쪽에 있는 경우가 많다.
4. 결과가 너무 적으면(세션이 10개 미만) 기간을 늘리거나 `--min-count 2`로 다시 돌린다. 어떻게 바꿨는지 사용자에게 말한다.

### 2단계: 여러 관점으로 반복 찾기

명령어 반복은 가장 찾기 쉽지만 가치가 가장 큰 경우는 드물다. cards를 아래 관점으로 하나씩 훑는다. 각 관점에서 최소 하나씩은 살펴보고 넘어간다.

| 관점 | cards에서 보는 신호 | 흔한 자동화 형태 |
|---|---|---|
| **같은 대상이 계속 나옴** | 같은 사내 도구·시스템·서비스 이름이 여러 세션 제목에 나옴 (예: 특정 VPN, 비밀번호 관리 도구, 특정 AWS 계정) | 그 대상 전용 스킬(구성·이전 결정·자주 쓰는 명령을 담음), 런북 |
| **남에게서 들어오는 일** | `타인발 요청?` 태그, "~래", "~왔거든", 동료의 오류 스크린샷 | 팀이 직접 쓰는 FAQ·셀프서비스 가이드, 문의 접수 템플릿, 팀 공용 스킬이나 봇 |
| **알림·보고가 오면 분석함** | "알림이 왔", "메일이 왔", 외부 보고서 첨부, 트래픽·보안·장애 원인 파악 | triage 스킬(정해진 순서로 1차 분석 → 보고 초안), 정기 점검 |
| **점검·관리를 그때그때 함** | 권한·계정·비용·사용 현황 조사가 이벤트가 생길 때마다 일어남 | 정기 감사 리포트(스케줄), 점검 스크립트 |
| **산출물 형식이 반복됨** | `Confluence작성`, `공지·가이드`, 계획서·정책 문서, 보고용 메시지 | 문서 템플릿 + 작성 스킬(위치·형식·검토 규칙 포함) |
| **같은 종류의 찾기** | "~어디야?", "이 URL 구현 찾아줘", 도메인 → 서버 역추적 | 맵·인덱스 문서, 찾기 스킬 |
| **개발 작업 반복** | summary의 C/CC/F 섹션 | 스크립트, hook, 스킬 |

**사용자 역할을 고려한다.** cards에서 사용자가 하는 일의 성격(개발, 인프라·보안 운영, 사내 도구 관리, 기획·문서, 팀 리딩 등)을 파악하고, 개인 작업 시간을 줄이는 후보와 **팀이나 조직 전체의 일을 줄이는 후보**를 둘 다 찾는다. 사내 AI 도입이나 운영을 맡은 사람이라면, 자기가 반복해서 답하는 일을 팀원이 스스로 해결하게 만드는 것이 개인 스크립트보다 효과가 큰 경우가 많다. 역할이 cards만으로 분명하지 않고 후보가 한쪽으로 쏠리면 사용자에게 한 문장으로 물어본다.

그다음 여러 섹션의 신호를 엮어 **사용자의 실제 업무 단위**로 후보를 만든다. 예를 들어 C의 `gh pr create`, F의 `pr create → checks → merge → docker compose up`, P의 "PR 머지해줘"는 서로 다른 후보가 아니라 하나의 "PR 올리고 CI 기다렸다가 머지 후 로컬 재기동" 흐름이다.

"git 커밋 자동화"처럼 누구에게나 해당하는 뻔한 후보가 나오면 그대로 두지 말고 실제 근거를 확인해 구체화한다.

```
python3 <skill>/scripts/scan_sessions.py trace --query "PR.*머지|merge" --limit 5
python3 <skill>/scripts/scan_sessions.py trace --session <8자리 세션ID>
```

`trace`는 해당 프롬프트 이후 Claude가 실제로 실행한 단계(명령, 수정한 파일, 사용한 MCP 도구)를 보여 준다. 이를 보고 다음을 파악한다.
- 매번 같은 단계인지, 매번 다른 판단이 필요한지 → 스크립트로 할지 스킬로 할지 정하는 근거
- 고정된 값(레포, 브랜치, 계정 profile, URL, 워크플로 이름)과 매번 바뀌는 값
- 사용자가 중간에 끼어들어 정정한 지점

다음 후보는 제외하거나 우선순위를 낮춘다.
- 이미 스킬·커맨드로 자동화된 것 (5번 섹션, 그리고 현재 컨텍스트의 스킬 목록)
- 한 세션 안에서만 반복된 것 (같은 작업의 재시도일 가능성이 높다)
- Claude 내부 습관 (`python - <<EOF`로 파일 수정, `git status` 확인 등). 이건 사용자의 반복 작업이 아니다.

### 3단계: 후보 제시

5~8개를 보여 준다. 개인 작업 후보와 팀·조직 후보를 나눠 각각 예상 절약 시간 순으로 번호를 매긴다. 번호는 두 묶음에 걸쳐 이어서 매긴다. 한 관점(예: 개발 명령어)에서만 후보가 나왔다면, 다른 관점을 다시 확인했는지 스스로 점검한다. 형식은 다음과 같다.

```
## 자동화 후보 (최근 30일, 세션 79개 분석)

1. **PR 올리고 CI 통과 후 머지 + 로컬 재기동** — 예상 절약 월 ~2시간 · 난이도 하
   근거: 6개 세션에서 `git add → gh pr create → gh pr checks → gh pr merge → docker compose up` 반복
         (55531e6f 09-28 my-api "결제 API 배포", b26d75a7 09-30 …),
         "3번 PR 머지해줘" 같은 요청 3회
   지금: 매번 Claude가 checks를 폴링하며 회당 ~18분

2. ...
```

- **근거**: 횟수, 세션 수, 대표 세션 2~3개(세션ID 앞 8자리, 날짜, 프로젝트, 제목), 마스킹된 실제 예시를 짧게 넣는다. 사용자가 "아 그거" 하고 알아볼 수 있어야 한다.
- **예상 절약 시간**: `월 환산 횟수 × 회당 소요(분) × 절감률`로 계산하고, 계산식을 괄호 안에 한 줄로 같이 보여 준다(예: `월 ~8회 × 15분 × 0.8 ≈ 1.6시간`). 팀 후보는 다른 사람이 아끼는 시간도 포함할 수 있지만, 그 부분은 가정이라고 밝힌다. 절감률은 스크립트·hook이면 0.8~0.9, 스킬이면 0.4~0.6(지시·확인 시간이 줄어듦), 규칙 추가면 0.2~0.3 정도로 잡는다. 소요 시간은 스크립트가 잰 활동 시간(10분 넘는 공백은 제외)이므로 "추정"이라고 밝힌다.
- **난이도**: 하(설정 한 줄 또는 짧은 스크립트, ~10분) / 중(스킬이나 스크립트 + 테스트, ~30분) / 상(외부 시스템 연동, 스케줄, 여러 레포).

마지막에 "번호를 고르면 자동화 방법을 제안할게요"라고 묻는다. 여러 개를 골라도 된다.

### 4단계: 방법 제시

고른 후보에 맞는 방법 2~4개를 번호로 보여 준다. 방법 목록과 각 방법이 맞는 경우·장단점·만드는 법은 `references/automation-methods.md`에 있다. 이 단계에서 먼저 읽는다.

```
### 1번 "PR 올리고 머지" 자동화 방법
1. **셸 스크립트 `prship`** (추천) — 장점: Claude 없이 몇 초에 끝남 / 단점: 충돌·CI 실패 같은 예외 판단은 못 함
2. **커스텀 스킬** — 장점: 실패 원인 분석·수정까지 이어서 함 / 단점: 매번 모델이 돌아 느리고 토큰 소모
3. **Stop hook** — 장점: … / 단점: …
```

추천은 하나만 하고, 2단계에서 본 근거(매번 같은 단계인지, 판단이 필요한지)로 이유를 한 줄 덧붙인다.

### 5단계: 구현 → 테스트 → 사용법

1. **계획 확인**: 만들거나 고칠 파일 경로와 각 파일이 하는 일을 보여 주고 승인받는다. 이미 있는 파일을 고치면 바뀌는 부분을 보여 준다.
2. **구현**: trace에서 본 실제 명령과 값을 바탕으로 만든다. 일반적인 템플릿이 아니라 사용자 환경(레포, 브랜치 규칙, profile, 워크플로 이름)에 맞춘다. 단, 비밀값은 파일에 하드코딩하지 않고 환경변수나 기존 자격증명 체계(aws sso, gh auth 등)를 쓴다. 스킬을 만들 때 skill-creator 스킬이 있으면 그 규칙을 따른다. settings.json을 고칠 때 update-config 스킬이 있으면 그것을 쓴다.
3. **테스트**: 실제로 돌려 본다. 부작용이 있는 작업(push, merge, 배포, 메시지 전송)은 `--dry-run`이나 읽기 전용 경로로 먼저 확인하고, 실제 실행 전에 다시 묻는다.
   - 스크립트: 실행해서 출력 확인. 잘못된 인자를 넣었을 때의 동작도 확인
   - hook: 샘플 JSON을 stdin으로 넣어 실행 (`echo '{"tool_name":"Bash",...}' | 훅스크립트`), 종료 코드와 출력 확인
   - 스킬: description이 트리거될 만한 문장 2~3개를 제시하고, 새 세션에서 실제로 호출되는지 확인하도록 안내
   - 스케줄: 한 번 수동 실행한 뒤 등록 상태 확인 (`crontab -l`, `launchctl list | grep`, CronList)
   - 성공 경로와 실패 경로(만료, 권한 없음, 입력 없음)를 둘 다 실제로 지나가 본다. 재현하지 못한 경로는 "미검증"이라고 사용자에게 분명히 말한다. 사용자의 로그인처럼 직접 해야 하는 단계가 있으면 `! 명령` 형태로 실행을 부탁한다.
   - 도구가 보여 주는 값의 의미도 확인한다. 예를 들어 캐시에 있는 만료 시각이 실제 세션 만료인지 자동 갱신되는 토큰의 만료인지 구분한다. 그럴듯하지만 틀린 표시는 없는 것보다 해롭다.
4. **사용법 안내**: 실행 방법, 끄거나 지우는 방법, 만든 파일 목록을 짧게 정리한다.

## 세션 시작 제안과 키워드 힌트 (플러그인 hook)

- **SessionStart**: 마지막 실행이나 제안 후 `interval_days`(기본 14일)가 지났으면 한 줄로 제안한다. 제안하는 순간 기록되므로, 무시하거나 거절하면 다음 주기까지 다시 묻지 않는다. 사용자가 그 제안에 "응"이라고 답하면 이 스킬을 바로 시작한다. 거절하면 아무것도 하지 않는다.
- **UserPromptSubmit**: "이번에도", "지난번처럼", "매번", "귀찮" 같은 표현이 보이면 세션당 한 번 힌트를 준다. 힌트를 받아도 요청을 가로채지 않는다. 지금 요청을 먼저 처리하고, 정말 반복 작업으로 보일 때만 끝에 한 줄로 제안한다.
